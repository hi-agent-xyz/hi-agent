# 量一次对话：口径、脚本、基线

每个 journey 都问"它是不是这样做的"，而**它多快、说了什么**这两件事，读对话是答不出来的——
快慢要秒表，说了什么要样本。这份文件是那把秒表：边界定义在哪、怎么跑、以及一条可以对比的基线。

工具是 [`scripts/measure-replies.py`](../../scripts/measure-replies.py)，`make measure` 跑它。
它只读 `data/memory/raw/`——host 自己写的线帧日志，每个 session 双向的每一条 JSON-RPC，
外加 text 通道自己的消息。**不读对话、不问 agent**，这是它能当证据用的全部理由。

    make measure                      # 默认 ./data
    make measure DATA=~/some/data     # 别的实例

## 三个时刻，其余都是从它们算出来的

| | 取哪一刻 | 从哪读 |
|---|---|---|
| **t0** | 你这条消息落到服务器 | `raw/text/<日>/text.jsonl`,`kind=message` 且 `from≠agent`,取 `message.ts` |
| **t1** | host 把你这条话作为 `## New signals` 发给 codex 的那次请求**发出** | `raw/sessions/<run>/reaction.jsonl`,`dir=send` `method=turn/start`,取帧 `ts` |
| **t2** | 这一轮里**第一个** `hi_say` 调用完成 | 同文件,`dir=recv` `method=item/completed` 且 `item.tool=="hi_say"` |

**A = t1 − t0，B = t2 − t1。** t0 是 `POST /api/in/text` 进 handler 那一行的 `Utc::now()`
([`text.rs`](../../src/foundation/server/text.rs))，和线帧同一个进程时钟,所以三个点之间没有跨机偏差。

**配对靠文本不靠时间**：t1 那一轮的 prompt 里 `## New signals` 段必须含这条消息原文
(去空白后前 60 字符相等)，且 t1 ≥ t0 − 2s，取最早一轮。一轮 turn 可能同时装着好几句话
(settle 窗口把它们攒成一批)，纯按时间配会配错。

两段各装着什么：

- **A** = settle 窗口 + **等上一轮 `turn/completed`**(loop 是串行的) + loop 开销。
  它是两个分布混在一起,所以中位数会骗人——脚本把它拆成"撞上了"和"没撞上"两行。
- **B** = codex 收到 prompt 到吐出第一个 `hi_say`。TTFT + 推理 + 决定说话。

两段都**不含** t0 之前(打字、到达服务器)和 t2 之后(sequencer/出声)。

一个边界上的坑：B 结束在**第一句**，而**你下一句排的队是排到 `turn/completed`**，不是排到
最后一句 `hi_say`。这两个差着中位 10.7 秒。

## 基线 · 2026-09-06

12 天,324 条人说的话,2820 个 reaction turn。**在
[`cf2127a`..`f27bc68`](https://github.com/hi-agent-xyz/hi-agent/commits/main) 那五个提交之前**——
所以这是复测要打败的那一份。

| | 中位 | p90 |
|---|---|---|
| A 说完 → turn/start | 5.7s | 43.3s |
| B turn/start → 第一句 | 18.3s | 35.2s |
| **A+B 说完 → 第一句** | **29.1s** | **70.1s** |

- **你开口时它正在跑：53%**，得等中位 18.9s。没撞上时 A 只有 **0.7s**——settle 窗口不是问题,
  串行才是。而且挡路的那些轮里 151/171 是它在回你**上一句**：这是对话轮次重叠,不是它忙。
- **一轮的地板：第一句 13.8s**,86% 的轮次在此之前收到 0 次 `tokenUsage` 更新,
  **就是一次上游请求**。那一次请求输出 227 token(其中 reasoning 136)、输入 103,283 token、
  命中缓存 98.7%。说 20 字和说 300 字差不到 3 秒——**这是固定成本,不是干活的代价**。
- **说完最后一句之后还要跑 10.7s**(p90 28.2s)。
- 第一句里 **17.7% 开头先复述**、5.7% 报时间估计;"完成后给你一份报告"和"有不清楚的我再问你"
  在 1948 句里 **0 次**。
- **账本被截断 25.9%**——`PROJECTED_TASKS` 当时是 12,超出的变成一句计数。

## 复测时看什么

那五个提交各自该在这份报告的哪一行上显形：

| `cf2127a` 账本不再截断 | 账本被截断 → **应归零** | 25.9% |
| `8bef9d2` 复述与时间估计 | 开头先复述 / 报时间估计 | 17.7% / 5.7% |
| `8c689c8` brief 带状态值 | 间接:见下 | — |
| `f27bc68` 两类 turn 的分叉 | 间接:见下 | — |
| `37fce40` reaction 的定位 | 间接:见下 | — |

后三条是提示词,**这份报告量不到它们**,因为"该一轮答完的有没有一轮答完"要读内容才知道。
量它们的办法是抽样:挑出问已知事情的短问句(状态、进展、还剩什么),看第一句是不是答案而不是
"我去查一下"。基线是 10 条里 6 条,而且那 6 条里有一半其实是"我去查"没被识别出来——
所以复测要**逐条读**,不要只看比率。

**这份报告量不到的还有两件事**,都在 [gaps.md](gaps.md) 里各有条目:哪些信息主动推给
Cognition(listener 144 条里 134 条是心跳),以及 Reaction 能不能被打断
(`features.steer` 每个 rung 都开着,只有 Cognition 在用)。

## 注意

- **`raw/sessions/` 会长到 GB 级**(一次实测是 11G)。脚本流式读,不整个装进内存,但第一次跑
  在机械硬盘上会慢。
- **只覆盖有线帧的那段时间**。`raw/text/` 通常比 `raw/sessions/` 留得久,所以老日期会配不上,
  报告里的"paired"数就是实际用上的样本量。
- **不要把这些数当性能基准**。它们量的是一个真人在真实一周里的体验,样本是他碰巧说了多少话;
  换一周会变。它们能回答的是"改了之后有没有变好",不是"这个系统有多快"。
