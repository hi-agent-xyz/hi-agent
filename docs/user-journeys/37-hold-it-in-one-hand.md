# 单手拿着它:对话是推上来的一页,划一下就回去

**Persona:** 同一个用户,这次只有 iPhone。他没有鼠标,没有键盘,一只手拿着手机,
拇指从屏幕下沿够上来。他不觉得自己在用一个「网页」,他觉得自己在用一个 app——
所以他对这个 app 的期待,就是他对手机上每个 app 的期待。
**Goal:** 点开对话 → 整屏;想回去 → 从左边缘划一下。翻 views 也一样。
按钮是手指按得着的大小,不是鼠标点得着的大小。
**Preconditions:** iPhone client(`CoreWebView.swift`)加载的是同一个 face;
`<html data-shape="phone">` 由 `lib/shape.ts` 判定(窄 **且** 粗指针)。
见 [`stage.md` § The phone stacks pages](../arch/stage.md)。
**与 [35](35-one-screen-across-devices.md)(一块屏)相连。**

---

## Steps & expected UX

1. **打开 app,什么都还没点** → 看到的是**房间**:presence、agent 摆上来的东西、
   底下右角一排控制。控制是 **44px**,拇指一按就中——不是菜单栏 popover 那套 32px。
   这一条是从缺陷倒推出来的:popover 大约 380px 宽,给它写的 `max-width: 420px`
   把手机也一起收窄了。宽度只答了一半的问题。
2. **点键盘那个控制** → 对话**从右边推上来**,整屏,没有圆角、没有浮在谁上面。
   房间在它下面,看不见了。
3. **页头是一条 bar**:最左一个 `‹`,右边挨着 mic / 喇叭 / 摄像头 / views / 关掉。
   还是那六个,一个没少——**键盘那个在这儿就是 `‹`**,因为从这一页里按它就是回去。
4. **拇指从左边缘往右拖** → 页跟着手指走,**一比一**,不是「识别到了手势然后播一段动画」。
   拖到一半松手 → 弹回去,什么也没发生。拖过大半、或者甩一下 → 页滑出去,回到房间。
5. **点输入行,键盘弹起来** → 行**停在键盘上沿**,而且**上面的消息也跟着往上收**——
   正在读的那几句还在屏幕上,不是被键盘顶没了。
6. **在对话页里点 views** → 第二页压上来。history 是**两列的图**(不是横着划的一条窄带),
   bookmarks 是会换行的 chip。再划一下 → 回到对话页,**对话还停在刚才那一句上**,
   没有重新加载、没有跳到底。
7. **横过来** → 变回房间那套排布(还是粗指针,但不窄了),再竖回去又是页。

## Expected outcome

- 三样东西:对话是页、views 是页、控制是手指大小。
- 一路推、一路划回来,滚动位置和已经拉回来的历史消息**一次都没丢**——
  `<Chat>` 从头到尾只挂载过一次。
- 桌面和 popover **一点没变**。

## Edge cases & failure modes

- **最左 20pt 里点一下** → 什么也不会发生(落在手势带上)。和 iOS 自己的边缘一样,
  页里的内容都从这条带子里侧开始。
- **对话页没有标题**:bar 就是它的头。一块手机屏不能一行写 "Conversation"、
  再一行放控制。views 页留了标题,因为一片缩略图不会自己说自己是什么。
- **正在往回拖的时候,房间的那排控制还没画出来** → 看得见的是它后面那块 view。
  松手落地就有了。认下的代价:另一条路是树里同时挂两排控制,那个更糟。
- **views 页里点一张卡** → 直接消失,没有滑出动画。选中一直就是立刻消失,所有 host 都一样。
- **WebKit 自己的左边缘手势**:`allowsBackForwardNavigationGestures` 关掉了。
  face 是一页,没有 back 可导航;它留着的只有一个跟我们抢同一条边的 recognizer。

_机制:`lib/shape.ts`(窄 **且** 粗 → `<html data-shape="phone">`,一个 flag,
CSS 和 JS 读同一个);`ui/PageEdge.tsx`(边缘拖拽,`--hi-page-x` 直接写在元素上,
不走 React state——一帧一次 re-render 整个 shell 是不能接受的);
`ChannelControls` 多一个 `bar`;`lib/softKeyboard.ts` 用 `visualViewport` 报键盘高度
(`dvh` 在 iOS 上答不了这个问题,`interactive-widget` WebKit 没实现)。
成熟度:**built,未实测**。_

## 实测

**还没有。** 以上在 Chromium 的手机模拟里验过:`data-shape` 判定、整屏几何、
44px 按钮、拖拽 1:1 跟手、拖过阈值提交、弹回、再次打开——都对。但模拟里的键盘不是
真键盘,安全区是 0,WebKit 自己的边缘也不在。**在真机上看过之前,这一页是「写完了」,
不是「见过它跑」。**

要看的,按顺序:

1. 键盘弹起时行有没有被顶掉(第 5 步)——这是最可能出问题的一条,
   因为 WebKit 会把 visual viewport 整个往上滑,而不是让页面滚动。
2. 刘海和 home indicator 的留白(bar 的 `--hi-safe-top`、foot 的 `--hi-safe-bottom`)。
3. 从对话页的滚动区域里往右划,会不会被滚动条抢走(手势带是 `touch-action: none`,
   但这是 iOS 上唯一一处只能靠真机确认的地方)。
