# 单手拿着它:房间里什么按钮都没有,从右边缘划一下,面板就进来

**Persona:** 同一个用户,这次只有 iPhone。他没有鼠标,没有键盘,一只手拿着手机,
拇指从屏幕边沿够过去。他不觉得自己在用一个「网页」,他觉得自己在用一个 app——
所以他对这个 app 的期待,就是他对手机上每个 app 的期待。
**Goal:** 房间里只有 agent 摆上来的东西,一个按钮都没有;要说话、要翻 views、
要开麦克风,**从右边缘划进来**;要回去看它摆的东西,**从左边缘划回去**。
**Preconditions:** iPhone client(`CoreWebView.swift`)加载的是同一个 face;
`<html data-shape="phone">` 由 `lib/shape.ts` 判定(窄 **且** 粗指针)。
手机只有两个 stop:`room` 和 `full`——390px 分不出两栏。
见 [`stage.md` § The panel, and the axis it runs on](../arch/stage.md)。
**与 [35](35-one-screen-across-devices.md)(一块屏)、[38](38-read-it-and-say-something-about-it.md)(桌面的中间那档)相连。**

---

## Steps & expected UX

1. **打开 app,什么都还没点** → 看到的是**房间**:presence、agent 摆上来的东西、
   一句字幕。**没有按钮**——一个都没有。角上那排六个控制没了,它占的那个角
   现在是 view 可以用的。这是这一页最要紧的一条,也是最容易做错的一条:
   房间是空的,那就得有别的路进去。
2. **拇指从右边缘往左拖** → 面板跟着手指进来,**一比一**,不是「识别到了手势
   然后播一段动画」。拖到一半松手 → 滑回去,什么也没发生。拖过大半、或者甩一下
   → 面板整屏落下来。
3. **面板整屏**:最上一条 head——左边 `Messages` / `Views` 两个 tab,
   右边 mic / 喇叭 / 摄像头 / 关掉 view,**44px**,拇指一按就中。
   下面是消息,最底下是输入行。**head 在每个 stop、每个 tab 上都一样**:
   没有哪个频道躲在某个模式后面。
4. **拇指从左边缘往右拖** → 面板跟着手指出去,同样一比一,同样是距离**或**速度。
   落地回到房间。
5. **点输入行,键盘弹起来** → 行**停在键盘上沿**,而且**上面的消息也跟着往上收**——
   正在读的那几句还在屏幕上,不是被键盘顶没了。
6. **点 `Views` tab** → 同一块面板换了内容,**不是压上来第二页**。history 是
   两列的图,bookmarks 是会换行的 chip。点回 `Messages` → **对话还停在刚才那一句上**,
   没有重新加载、没有跳到底。
7. **在 Views 里点一张卡** → screen 跟着走,而且**面板自己退回房间**,
   因为它正盖着那张卡要去的地方。
8. **横过来** → 变成 `wide`(还是粗指针,但不窄了),多出中间那一档;
   面板原来开着就还开着,只是变成靠右一栏。再竖回来又是整屏。

## Expected outcome

- 房间里**零个按钮**,面板里**四个频道一个不少**。
- 一根轴,两个方向,一个手势:右边缘进,左边缘出。没有第二种关法要记。
- 一路推、一路划回来,滚动位置和已经拉回来的历史消息**一次都没丢**——
  `<Chat>` 从头到尾只挂载过一次,`room` 是这个盒子被推到屏幕右边外面,不是它不存在了。

## Edge cases & failure modes

- **右边缘 20pt 里点一下** → 面板进来一档(点击就是进一档,拖也是)。
  这是给鼠标留的门,手机上顺带也有。
- **`room` 的时候左边缘 20pt 里点一下** → 什么也不会发生,而且**那条带子根本没挂**:
  没有可退的地方就不挂退的带子,所以一块 board 的最左 20pt 不会被白白吃掉。
  同理 `full` 的时候右边那条也不挂。
- **面板没有标题**:head 上的 tab 就是标题。对话里原来那行 "Conversation" 删掉了——
  它和上面一行的 `Messages` 是同一个词隔一行写了两遍。
- **正在往回拖的时候,view 不会跟着重排** → 重排只在松手落地那一下发生一次。
  一块编译出来的 board 一秒重排六十次是不能接受的。
- **WebKit 自己的左边缘手势**:`allowsBackForwardNavigationGestures` 关掉了。
  face 是一页,没有 back 可导航;它留着的只有一个跟我们抢同一条边的 recognizer。

_机制:`lib/panel.ts`(轴本身——哪个 shape 有哪些 stop、怎么走、松手落在哪,
纯函数,可以摆一张数字表测);`ui/PanelEdge.tsx`(两条边缘带,
`--hi-panel-left` 直接写在元素上,不走 React state——一帧一次 re-render 整个 shell
是不能接受的);`ui/Panel.tsx`(head 不变、body 换 tab);
`lib/softKeyboard.ts` 用 `visualViewport` 报键盘高度(`dvh` 在 iOS 上答不了这个问题,
`interactive-widget` WebKit 没实现)。
成熟度:**built,手机形态在 Chromium 模拟里看过,真机未实测**。_

## 实测

**2026-09-07,Chromium 无头(390×844,粗指针模拟),macOS。** 看过的:
`data-shape=phone` 判定对;开机停在 `room`;只挂了右边那条带子;
按钮 44px;从右边缘拖 385→60 落到 `full`,`--hi-panel-left` 变 0;
`Messages`/`Views` 两个 tab 在;从左边缘拖 6→360 回到 `room`。
`inert` 在 `room` 上真的生效了——面板里 0 个可 tab 到的东西
(**这一条差点漏掉**:React 19 把 `inert=""` 当成 false,写成布尔才对)。

**没看过的,按要看的顺序:**

1. 键盘弹起时行有没有被顶掉(第 5 步)——最可能出问题的一条,
   因为 WebKit 会把 visual viewport 整个往上滑,而不是让页面滚动。
   模拟里的键盘不是真键盘。
2. 刘海和 home indicator 的留白(head 的 `--hi-safe-top`、foot 的 `--hi-safe-bottom`)——
   模拟里安全区是 0。
3. 从面板的滚动区域里往右划,会不会被滚动条抢走(带子是 `touch-action: none`,
   但这是 iOS 上唯一一处只能靠真机确认的地方)。
4. **零按钮的房间在真人手里到底找不找得到路。** 这是这次改动最大的一笔赌:
   桌面还有「打字就开」和边缘 hover 那根细线,手机只剩边缘划这一条。
   模拟器答不了这个问题,只有人能答。
