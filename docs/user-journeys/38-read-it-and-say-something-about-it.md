# 一边看它摆上来的东西,一边说话:面板把 view 挤窄,而不是盖住

**Persona:** 桌面用户,1512px 的窗口。agent 刚摆上来一块 board,他想边看边问。
他不想为了打字把 board 遮掉一块,也不想为了看 board 把刚说的话关掉。
**Goal:** 房间(整块 board)· 中间那档(board 窄一点 + 面板)· 整屏面板,
三档之间来回,而且**是他自己在动它**。
**Preconditions:** `wide` 形态(不是窄、或者不是粗指针)。
三个 stop 都有:`room` / `panel` / `full`。
见 [`stage.md` § The panel, and the axis it runs on](../arch/stage.md)。
**与 [37](37-hold-it-in-one-hand.md)(手机只有两档)相连。**

---

## Steps & expected UX

1. **刚打开一个窗口** → 停在**中间那档**:左边是房间,右边 420px 是面板,
   开着 `Messages`。手机开机停在房间,桌面不是——因为桌面原来那个角上的六个按钮
   没了,一块全白的纸没有任何一个看得见的入口。宽窗口装得下两样,那就都给。
2. **agent 摆上来一块 board** → board 排进 **1092px**,不是 1512px 里被盖掉 420px。
   **它是完整的**,只是窄一点:右下角那一块没有藏在什么东西后面。
3. **拖两块屏的交界处**——也就是面板自己的左边沿,不是窗口的左右边——**往左拖**
   → 面板变成整屏,board 让位。**拖的过程中面板不重排**:它一直按落定的宽度排,
   跟着手指的是那条边,露出来的是已经排好的东西,不是一帧比一帧宽的重排。
4. **同一条边往右拖两次**(或者 `Esc` 两次,或者 `←` 两次)→ 整屏 → 中间档 → 房间。
   整屏时那条边就是窗口的最左边,中间档时它回到交界处——**一个把手,它永远在
   两块屏碰头的地方**。
   到房间时 board 拿回整块 1512px,**上面一个 host 的东西都没有**,
   只剩最新那句话的字幕,几秒后自己淡掉。
5. **随便敲一个可打印的键** → 面板开到中间档、切到 `Messages`、这个字符落进输入行。
   这是桌面第二条进得去的路,而且它一直就在。
6. **鼠标移到那条边上** → 带子上浮出一根很淡的细线。移开就没了。
   这是**唯一**画出来的入口提示,而且只在细指针上画。开机停在中间档,
   所以这根线第一眼是在交界处,不是在窗口的最右边。
7. **在那条边上点一下** → 退一档(整屏 → 中间档 → 房间);**在房间里点它**
   → 进一档。鼠标能一路走出去,也能一路走回来。
8. **触控板两指横扫** → **面板跟着两指走,一比一,和拖那条边一模一样**,
   而且**在屏幕任何地方都行,不用去够那条边**。往右扫(手指往左)面板进来,
   往左扫出去——和同一只手拖那条边是同一个方向。扫一半停手 → 滑回去,
   什么也没发生;扫过大半 → 落到下一档。笔记本上这是唯一一个
   不用先找到什么才能用的入口。
9. **顺着往下读长对话,两指从来不是完全竖直的** → 面板不动。
   横向要比纵向多一倍才算数;不算数的那一下会把这一轮清掉,
   不会把偏移攒到下一次。

## Expected outcome

- **board 从来不会被盖住**,只会被挤窄——而且挤它的永远是人,不是 agent。
  agent 摆东西不动面板,面板在哪就在哪。
- 一根轴,三档,四种走法(拖 / 点 / `Esc`+方向键 / 打字),没有第二套关法。
- 面板换 tab、换 stop、关掉再开,**对话都停在原来那句上**。

## Edge cases & failure modes

- **指针底下有个能横向滚的东西时,两指横扫是它的**,不是面板的——views 那两行、
  任何带宽表格的 board。而且不看它还剩不剩得滚:滚到头之后把下一下交给整块面板,
  比它就停在那里更吓人。
- **一次横扫最多走到隔壁那一档,扫多狠都一样**——不是不让它跟手,是**那条边被拦住了**
  (`reach`)。触控板抬手之后惯性还在往外发帧,而哪一帧是手推的、哪一帧是惯性,
  没有诚实的办法分得出来;所以边只走到人可能想让它停的地方,多出来的惯性顶在挡位上,
  不产生位移。从房间狠狠扫一下会停在 view 旁边,不会一路盖住它。
- **拖那条边不受这个限制**。手指或鼠标按在边上,每一个像素都是手走的,
  所以一次长拖仍然可以横穿整根轴。这条不对称是两只手的区别,不是两处不一致。
- **要先「抓住」才动**:横向攒够 24px 才握住那条边,所以一次歪了的滚动不是横扫;
  没攒够之前那些帧还是浏览器的。
- **松手到落档之间有一拍**(~120ms):没有结束事件可等,帧停下来才算这一轮完;
  狠狠一甩的话还要等惯性烧完。那时候面板已经顶在挡位上了,所以这一拍拖的是
  「记下来」,不是动作本身。
- **面板最右 20px 现在点得着了**。原来那里站着「再进一档」的带子,是整根轴上唯一
  一处真的吃掉可点区域的地方;一个把手之后它还给面板了。代价是**鼠标点不出
  「中间档 → 整屏」**——点是往房间走的,要变宽就拖那条边,或者按 `→`。
- **落定那 260ms 里,窗口和里面那个盒子不一样宽**。整屏 → 中间档时看得见:
  内容已经收成 420px,窗口还在往回缩,前面领着一条面板自己的玻璃。
  反过来变宽看不见。换来的是拖动全程不重排。
- **有的 view 在 1092px 下排不好看** → 认下的代价。一块 view 是照着交给它的框
  编译出来的,1512→1092 是真的换了框。付得起是因为**是人自己拖的**,
  而且再拖一下就是整屏。真要治,是把 view 写成能窄,不是让 host 不敢挤。
- **拖到一半松手** → 就近落档;甩一下 → 顺着方向走**一档**,不会从房间一路甩到整屏。
- **一个 view 抢走了方向键** → 焦点在 view 里的时候方向键是它的(`lib/keyboard.ts`),
  这时候只有边缘手势和 `Esc` 还管用。这是 plane 规则,不是例外。

---

_机制:`lib/panel.ts` 的 `stops("wide") = [room, panel, full]`、`settle()` 和
`measureOf()`(两档宽度,拖动不动它);
`.hi-root[data-stop="panel"] .hi-plane--view { right: var(--hi-panel-width) }`
——**「挤」就是这一条规则**,而且只挂在落定的 stop 上,不挂在拖动过程中;
`ui/PanelGesture.tsx` 一条带子,骑在 `--hi-panel-left` 上,所以它自己就在交界处,
外加根元素上一个 `wheel` 监听——触控板那一路;两路共用同一份 drag 记录,
区别只在「谁说边该在哪」和「怎么知道松手了」。`lib/panel.ts` 的
`rolled()` / `sideways()` / `reach()` 是触控板那一路的算术。
成熟度:**built,Chromium 无头里用真的鼠标和滚轮事件走过一遍,真人只用过"找不到入口"这一步**。_

## 实测

**2026-09-07,Chromium 无头(1512×900),macOS。** 逐条对过:
开机停在 `panel`;`--hi-panel-left: 1092px`、view plane `right: 420px`;
右边缘点一下 `room→panel→full`,左边缘点一下 `full→panel`;
从左边缘拖 8→900 回到 `room`,从右边缘拖 1505→1000 回到 `panel`;
拖完元素上那个内联的 `--hi-panel-left` **清干净了**(不留一个过期的像素值);
`Esc` 一档一档退;敲 `k` → 开到 `panel` + `Messages` tab。

**真的把一块 view 摆上去看过**:从 `Views` tab 点开 `Stats`,
它在 1092px 里重排,面板在旁边**没盖住它任何一块**;退到 `room`,
它拿回 1512px,屏幕上再没有别的东西。两张截图并排看,重排是干净的。

**2026-09-08 复测(同机同尺寸,CDP 派真的鼠标事件,面板改成两档宽度 + 交界处
把手之后)。** 看过的:开机 `panel`,面板 `1092..1512`,里面那个盒子同宽,
带子 `1082..1102`——**骑在交界处**,不在窗口边上。
按住交界处往左拖 1050 → 900 → 700 → 500 → 300:面板窗口一比一跟着手指,
**里面那个盒子从头到尾停在 `1092..1512`,一次都没重排**;松手落 `full`,
元素上的内联变量清干净了。反过来从房间的右边沿往里拖 1450 → 1000:
面板从 54px 长到 504px,盒子一直是 420px——**是露出来,不是长出来**。
点:整屏点最左 → `panel`,中间档点交界处 → `room`,房间点最右 → `panel`。
一路走出去又走回来,鼠标全程够用。

整屏下两个 tab 都量了:输入行 `340..1172`(832px 居中),**和消息那一栏
一模一样宽**——原来它是横跨 1512px 的。views 的 chip 会换行、不再横向滚。
history 那一格没看成:这台是干净的 data dir,trail 是空的,`.hi-views-strip`
压根没渲染。**改的那条 track 是在样式表里量的**:1512px → 5 列、tile 287×162
(原来是 9 列、152×85,比侧边栏的 160×90 还小);1024px → 5 列、190×107。
手机那头是从规则本身推的,不是量的——`clamp(150px, 18vw, 260px)` 在视口
833px 以下恒等于 150px,和原来那个固定值是同一个数(无头 Chrome 的窗口
最窄只到 500px,390px 量不了)。

**2026-09-08 再测(触控板两指横扫落地之后,CDP 派真的 `mouseWheel`)。**
右扫 90px:`panel → full`;同一轮里再补 800px 的惯性:**还是 `full`**,一扫一档。
左扫 `full → panel`,再左扫 `→ room`,右扫 `→ panel`——整根轴两指走得完。
按 `deltaY:110 / deltaX:6` 连发 30 帧(**横向一共漂了 180px**,远超 60px 的门槛):
**面板一动不动**——这是最要命的那条,读长对话时面板自己关掉的话这张脸就没法用了。
指针放到 bookmarks 那一行上横扫:面板不动,**那一行自己滚到了 160px**。

**为什么加这一路,记一下**:是**人用出来的**,不是读文档读出来的——
「桌面上不知道怎么把它调出来」。下面第 1 条问的就是这件事,
它以唯一可能的方式得到了回答:**答案是找不到**。

**2026-09-08 三测(横扫从「一扫一档」改成跟手之后,同样是 CDP 派真的 `mouseWheel`)。**
跟手:每来 30px,面板左沿就走 30px(1092 → 1062 → … → 912),`data-dragging` 在,
**里面那个盒子一直是 420px**——跟拖边一样,是露出来不是重排。
挡位:从房间一轮发 2000px,边**停在 1092 一动不动**,松手落 `panel`——
惯性顶在挡位上,没把面板推过头。慢扫 150px:边走到 942,松手**弹回 `panel`**
(反悔了就什么也没发生);慢扫 700px:边走到 392,落 `full`。
不该动的还是不动:18px 的横向轻推(没到 24px 的抓取阈值)、
`deltaY:110 / deltaX:6` 连发 30 帧,面板都纹丝不动。
重构之后**拖那条边照旧**:从交界处按下拖 1092 → 1000 → 800 → 600,一比一,松手落 `full`;
点最左那条带子退回 `panel`。

**没看过的:**

0. **真机的惯性到底有多长、跟手跟得稳不稳。** 这是现在最该看的一条:
   无头里派的 `mouseWheel` 是干净的——**没有真的惯性尾巴**、没有 `deltaMode`
   报 lines 的触控板、也没有 macOS 自己的「滑动来回切换页面」在旁边抢。
   上面那 2000px 是手写的、匀速的假惯性;真机的尾巴是衰减的,长短也不一样。
   要看的是两件事:松手到落档那一拍会不会长到觉得卡;以及 `REST_MS`(120ms)
   会不会短到把一次「中途停一下再接着扫」切成两轮。这两个数都是能调的旋钮。
1. **真人的手指在交界处拖起来是什么感觉。** 这次改动的整个理由就是「拖那条边
   才是直觉」,而 CDP 派出来的鼠标事件答不了直觉这个问题。
1. ~~**真人在一块全白的房间里找不找得到那条边。**~~ **2026-09-08 有答案了:
   找不到。** 这条不再是「没看过的」,它是触控板那一路存在的理由。
   剩下的那半个问题是**只有鼠标、没有触控板的桌面**——那里还是只有那条细线、
   键盘,和开机就开着的面板。
2. 一块**排得不好**的 view 在中间档下什么样。`Stats` 排得很好,不能代表全部——
   要找一块有固定宽表格的。
3. 菜单栏 popover(~380px,`wide` 但只有一栏宽)下中间档退化成整屏对不对。
