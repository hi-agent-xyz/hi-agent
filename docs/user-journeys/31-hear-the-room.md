# 听见整个房间,但只在该接话时接话

**Persona:** 老板和其他人在同一个房间里说话,Hi Agent 的麦克风会持续听见所有人的声音。
**Goal:** Hi Agent 像在场的人一样判断一段话是不是在跟自己说;不被旁聊、电视和识别碎片带跑,又能在后来相关时想起刚才听见的内容。
**Preconditions:** 麦克风已开启;ASR 只负责转文字,diarization 只负责给声音标出已知身份或稳定但未知的 speaker id。它们不判断话是不是说给 Hi Agent 的。

## Steps & expected UX

1. **老板正和同事讨论午饭,其中出现几个问句** → Hi Agent 听见这些话,但不插嘴、不追问"是在叫我吗"、不派任务。问句形状本身不等于在问它。
2. **一个 Hi Agent 认识的声音问同事"你下午有空吗?"** → Hi Agent 仍保持安静。认识说话人只说明"谁说的",不说明"说给谁"。
3. **一个尚未认出的声音转向 Hi Agent 说"帮我看看明天会不会下雨"** → Hi Agent 根据正在发生的语义交换接话并处理,不因为 speaker 是 unknown 就忽略,也不要求先喊名字或 wake word。
4. **同事之间提到"上海会议改到周五了"** → Hi Agent 不回应,不把它当成老板的指令、承诺或已确认事实,也不因此启动工作;这句话只作为近期外围语境轻轻留着。
5. **稍后老板问"她刚才说会议改到哪天?"** → Hi Agent 把新问题和刚才的旁聊连起来,回答"我听到的是周五"。若 speaker 归属或 ASR 字词不确定,回答中保留这份不确定,不补成确定事实。
6. **电视里传来"你准备好了吗?"或远处只识别出半个问句** → Hi Agent 不作答。背景媒体、噪声和残句不能仅凭关键词或问号取得它的注意。
7. **老板已经在和 Hi Agent 讨论行程,接着自然说"那就帮我订下午那班"** → Hi Agent 继续这段交换并采取正常的确认或执行动作。直接请求不必包含名字或 wake word;是否接话取决于上下文语义。

## Expected outcome

- 麦克风可以听见整个房间,但 Hi Agent 只在语义上参与自己的交换。
- "听见"不等于"被叫到";沉默是参与边界,不是把输入丢掉。
- 旁聊不会触发回答、任务、委派或对用户的错误记忆。
- 近期外围语境在后来被明确关联时可以回到焦点,让 Hi Agent 回答"刚才说了什么"或接上先前线索。
- 已知身份、未知 speaker id、关键词、问句形状和是否喊名字都只是证据,没有任何一个能单独决定要不要回应。

## UX principles

- **感知保持机械:** ASR 产出文字,diarization 产出说话人归属;不要在感知层提前删掉"不像是在跟我说"的内容。
- **Reaction 按语义决定参与:** 看整段上下文、当前交换关系、话在承接什么,再判断这是不是自己的回合。
- **外围不是遗忘:** 无关话语先不进入行动和信念,但短期内保留足够语义,以便后续问题让它变得相关。
- **不依赖 wake word:** 喊名字可以是证据,不能是硬门;没喊名字的自然承接也应被听懂。
- **不冒领别人的对话:** 不确定是否在跟自己说时,优先从语义和后续上下文消解,不要习惯性插入一句确认来打断现场。

## Edge cases & failure modes

- **多人同时说话,diarization 串人** → 以内容和交换连续性判断是否接话;需要引用刚才内容时说明"我听到有人说……",不凭不稳的 speaker id 强认身份。
- **旁聊里出现 Hi Agent 的名字** → 名字只是局部证据;若整句是在向别人介绍或谈论 Hi Agent,仍不接话。
- **用户从旁聊突然转向 Hi Agent** → 允许同一串音频从外围变成直接交换;不要求另起一句或重新唤醒。
- **旁聊包含像任务的命令句** → 不执行、不委派、不写成 open task;只有后续语义明确把任务交给 Hi Agent 时才接住。
- **后来追问的内容已经听不清** → 如实说只听到的部分或没听清,不根据上下文补写原话。
- **环境持续嘈杂** → 沉默不能阻塞直接对 Hi Agent 的新话;Reaction 每一轮都重新根据最新语义判断参与关系。

## Open questions

- 所有环境语音是否都应作为普通 user message 出现在可见 transcript 中,还是需要在界面上区分"直接交换"和"环境听见"?当前 journey 只规定行为,不规定最终呈现。
- 外围语境保留多久、以原始 transcript 还是轻量摘要进入近期上下文,需要结合延迟、隐私和 token 成本确定。
- 明确无关的背景媒体是否需要更早降权,可以优化,但不能让感知层变成不可恢复的 addressed/unaddressed 硬门。
  **已定 2026-09-22:** 降的是唤醒，不是内容。只有房间（`audio` / `vision`）的一批，由 host 问 System One 一句「有没有人在跟 agent 说话」，答不是就不唤醒 Reaction，这批进旁听区，下次别的东西唤醒时在 `## Heard around you` 下一起带进去；答不清、超时、出错都照常唤醒。见 [host.md § The room screen](../arch/host.md#the-room-screen)。

_机制:ASR 出文字,diarization 出说话人切分,`foundation::acoustics` 出这段声音本身的物理量——房间里有几个人在说话、这一段是不是最近的那个、是清楚还是糊在噪声里、有没有压着别人的话;都以 `⟨room: …⟩` 挂在 transcript 上,只在情况变化时出现。全部是尺度无关量(同一次采集内两个电平之差,或这个说话人对房间里其他人),所以不依赖麦克风增益。Reaction 从这些证据加上近期语义判断交换归属与 floor;感知层不做 addressed/unaddressed 判定,一句都不丢。唯一的例外在感知层之后：一批只有房间的输入唤不唤醒 Reaction，由 host 的 room screen 决定，被放下的行随下一次唤醒带进去（[host.md § The room screen](../arch/host.md#the-room-screen)）。_

## 待实测 2026-09-04 · 已建未观测

声学证据、按 speaker 聚合的声纹判定、`⟨room: …⟩` 标记都已落地并有单元测试,**但从未对着真实房间跑过**——阈值(近/远 6 dB 与 12 dB、清楚/糊 20 dB 与 12 dB、60 秒窗)全是估计值,只在合成信号上验过。要测的:

- 两个人在房间里说话,一个贴着麦、一个在远处 → 远的那句是否带 `far off`,近的是否带 `the closest`。
- 电视 / 背景人声 → 是否稳定读成 faint 或 far off,而不是和正对麦克风的话无从区分。
- 同一个人连续说 → `⟨voice: …⟩` 只在换人时出现,不是每句都挂。
- 认识的人在跟别人说话、陌生声音直接对 Hi Agent 说 → step 2 与 step 3 的行为是否真的分开。
- 一次识别不再写库:跑一轮之后 `data/memory/facets/people/` 不应冒出新的一样本簇。

## 离线重放 2026-09-21 · room screen 的依据

不是对着活实例测的：是把 08-15 到 09-20 帧日志里**只由房间音频 / 摄像头唤醒的 650 个 Reaction turn** 原样交给 System One（`jev-1.13.0`），再和一份盲标对照。盲标是三个模型读者各标三分之一，看不到分数，也看不到 Reaction 当时的反应——**不是赵力标的**。

- **这 650 批里一半是在跟它说话。** 297 批确实在跟 agent 说（大多是语音口述、对着它做的页面讨论、拍照游戏），20 批是这种话的碎片，322 批是闲聊 / 导航语音 / 识别噪声，11 批判断不了。
- **Reaction 自己判得不差。** 对它说的它接了 94%（280/297），闲聊它有 8% 也搭了话或做了事（26/322）。
- **第一种问法不行。** 逐句问「这句是不是对它说的」、不带时间：09-09 口述海报排版 0.10–0.15，家里吃饭闲聊 0.10–0.11，分不开。要挡掉 45% 的闲聊就得误挡 2 个真请求。
- **第二种问法可用。** 带上每行「几秒前」和「agent 上次说话是几秒前」，按整批问「有没有人在跟它对话，哪怕没点名」（AUC 0.947）。阈值 0.30：挡掉 164/322 批闲聊（51%），误挡 1/297——09-08 读书讨论的开场白「我现在正在看这个小红书上的整理」，按设计会随下一句一起带进去。Reaction 误搭理闲聊的 26 次里挡掉 8 次。阈值是在同一批数据上挑的，数字偏乐观。
- **挡不住的一类。** 09-13 他在给别的应用做语音输入，「你检查一下我的 download 文件夹」得分 0.93。光看文字谁也分不出，事后他说了才知道。
- **延迟。** 从开发机经托管网关逐次调用，约 1.6K 输入 token，p50 580 ms，p90 1.06 s。
- 挡掉的集中在吵的日子：08-30 家里 55 批，09-16 多人开会 45 批，平均一天 4 批左右。

## 实测 2026-09-22 · room screen 接通，合成语音，不是真房间

scratch 实例（独立 `--data-dir`，BYOK 直连网关的 decision / llm / stt，reach 关），用 macOS `say` 合成两段中文语音，走真的 `POST /api/in/audio` → STT → reaction 循环：

- ✅ 「宝宝快来吃饭，饭都要凉了，先去洗个手」：`room screen p=0.06 wake=false ms=707`，**没有起 Reaction turn**。
- ✅ 随后「你好，你能听到我说话吗？」：`p=0.87 wake=true ms=701`，turn 的输入里 `## Heard around you` 带着上一句，在 `## New signals` 前面；它照常回话。
- ✅ 延迟：问题在这句话进队时就发出去了，答案回来时正好是 700 ms settle 关闭的时刻，没有多等。
- 🟡 冷线程的第一轮里，那句闲聊同时出现在 `## Recent (last 30 minutes)` 和 `## Heard around you`——冷开时整段 recent tail 会重发，热线程只有后者。

## 待实测 2026-09-22 · room screen 没在真房间里观测过

- 吵的房间（家里吃饭、多人开会）里，`server.log` 的 `room screen` 行：`p`、`wake`、`ms` 分布是否和离线重放一致；被放下的批次是不是真的闲聊。
- 对它说的话被放下时（`wake=false` 而下一轮 `## Heard around you` 里有给它的话），它是不是当成「晚了、被等着的话」来接。
- 安静场景下的延迟：直接对它说一句，回复有没有比以前慢。
- 没做的一半：turn 在生成时进来的闲聊仍然会让回复被判「过时」（host.md § Open），这次不管。
