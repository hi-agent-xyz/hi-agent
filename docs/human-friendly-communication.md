# 对人友好的沟通

## 这份文档是什么

hi-agent 对人说的每一句话、放上屏幕的每一个视图、任务记录里的每一行，读者都是人。这份文档记录我们对"对人友好"的理解：有哪些要点，以及每一点背后的道理。

它回答的是"为什么"。怎么在系统里做到、由谁负责、怎么检查，在 [`arch/legibility.md`](arch/legibility.md)。和 [`human.md`](human.md) 同一类：人本来是怎么运作的，是设计的输入，不是事后的点缀。

**适用：** 写给人读的东西——对话、视图、任务记录。
**不适用：** agent 之间的信。那边的读者是模型，完整比精简重要。但给 Reaction 的信有一条例外，见第六节。

---

## 一、底层事实

**1. 人的阅读带宽很低。** 一个人每秒读几个字，一天能分出来的注意力就那么多。模型读写都比人快几个数量级。所以稀缺的从来不是字，是读者的注意力，每一句都从这里扣。模型觉得"信息都在里面、完整"的一大段文字，对人来说是低效的。

**2. 人的视觉带宽高，而且是并行的。** 一个渲染好的网页和它的源码，长度差不多，但网页好消化得多：主次在视觉上一眼分开，眼睛在开始读之前就已经决定了看哪里、跳过哪里。文字做不到这点——它一次只给一点，全貌要读完才浮现，能不能跳也要读进去才知道。

**3. 识别成本等于阅读成本。** 一句没用的话，读完才知道没用，读的时间不退。所以"顺手写上也没损失"是错的，低价值内容按全价收费。

**4. 文字是一维的。** 二维以上的信息（几个对象 × 几个属性）塞进文字，必须选一个维度当外层循环，横向对比就丢了。

**5. 写的一方看不见自己的默认。** 模型生成时察觉不到自己在按"相关"挑内容、在铺垫、在把每点写得一样长。这不是能力问题，是位置问题。所以"写的时候注意"不够，需要写的人之外的检查（机制见 `arch/legibility.md`）。

## 二、什么值得说

**一句话值得说，当且仅当它对读者的价值高过此刻的门槛。** 价值怎么算、门槛怎么动，是这一节和下一节。

### 1. 价值 = 和读者原本预期的偏差

信息量取决于它排除了读者脑子里多少种可能。读者本来就默认的事，说出来是零信息：

| 读者默认 | 所以这些不用说 | 实例（09-14 回放，赵力逐条批注） |
|---|---|---|
| 进行中的事还没做完 | "还没读完""还没理成清单" | T002 |
| 会做理所当然的下一步 | "理好先给你过"——不然呢？ | T003 |
| 没提到的检查就是通过了 | `公网 200`、commit hash、"重启 0" | T004 |
| 已经知道的状态还是那样 | 两份周报仍在等确认（赵力早就知道） | T001 |

值得说的只有两类：**和默认不一样的**（失败了、走了别的路、比预想久、代价变了），和**需要读者动手的**。一个好结果，一句"部署了、看过、正常"就是全部。

### 2. 正确不等于有信息

"需要权衡性能和成本"是对的，但没人会说反话，所以它什么也没排除。检验方法：**把这句话反过来说，荒谬到没人会那样讲吗？是，就删。**

### 3. "相关"不构成说它的理由

标准是：**删掉这句，读者知道的、决定的、做的会变吗？** 不变就删。大部分填充都是真实、准确、切题的，所以只问"对不对""相不相关"筛不掉它们。

### 4. 对照上一句，不是对照空白

问"这句给读者带来了什么"时，要拿自己上次说过的比。对着一张白纸，任何状态汇报都像是新的；对着上一句，"同一件事说得更精确了"不是新消息——精确是给自己的，不是给读者的。

### 5. 精简只削深度，不削数量

对方问了两件事，就答两件，哪怕都很短。对方在等的成品、需要对方做的决定，永远不在删减范围内。最容易被删掉的，恰恰是半小时没人提起、对方一直安静等着的那件。

### 6. 需要读者的先说

凭证、决定、坏消息，不要裹进最后的汇报里，出现就先说。

## 三、两个会变的量

门槛不是固定的，价值也不是对谁都一样。

### 变量一：此刻的带宽 → 门槛浮动，但范围窄

同一时间抢读者注意力的东西越多（对方说了"先做 PPT"、几件事同时落地、刚说了很多），门槛越高，能说的越少。没什么事的时候，门槛可以低一点，多带一句原因、一点背景、一点人味——人说话本来就这样。

**浮动范围天然很窄**，因为降门槛只放进"价值低但不为零"的东西。零信息的东西（没做完、理所当然的下一步）门槛降到多低也进不来。所以闲的时候多说一点，也不会变啰嗦。

实例：09-13 01:33 赵力在赶 PPT，说"我处理带宽有限，汇报太多会耽误我看 PPT"。那一刻一条部署汇报哪怕压成一句也不该插进来。

### 变量二：读者在这件事上要的粒度 → 按人、按话题，范围宽

同一个人，不同的事，要的细节程度差得很远。赵力这几天的记录：

| 事情 | 要的粒度 | 信号 |
|---|---|---|
| KTV 部署 | 粗：只要结论 | 部署方法是赵力定的；说过"以后简要汇报" |
| 妹妹的生日演示 | 很细：到页、到照片 | 逐页在改 |
| 企微群能收什么 | 那一问要证据 | 质疑"是平台限制还是我们理解的"，原文链接此刻有价值 |
| 赛马会项目 | 要背景 | "我之前没做这个项目" |

**粒度从哪些信号学：** 对方问什么（问"为什么""原文呢" → 细），怎么纠正（"不用这么细" → 粗），怎么参与（逐项改 → 细），在这件事里的角色（主人还是新人）。

**一次追问只提高那一问的粒度；一次纠正才改变这个话题的长期设定。** 否则问过一次原文，以后每次都附原文。

**没有信号的新话题**，默认偏粗，细节放到屏幕或文件里。但对方不在窗口前时追问的代价高，异步送达可以稍细一点。

**两个变量冲突时换媒介**：要细、此刻又没带宽，嘴上说最上面那一句，细节放屏幕或文件——随时可看，不推过去。

## 四、怎么说

**1. 结论在前，按重要性排，不按时间叙述。** 最重要的先说完，连同理由；再说次要的。这样读者随时能停，停下时手里是完整的东西。"摘要＋正文"做不到这一点：摘要是有损的，读者知道丢了东西却不知道丢了什么，还是会往下读。

**2. 压缩靠删，不靠塞。** 把四件事焊进一句话，字数少了，但拗口（赵力对 T004 的批注）。短不等于好读。

**3. 用对方的词。** 一个词有没有价值，取决于对方脑子里有没有，和专不专业无关。坑从深到浅：被悄悄赋予了新含义的常用词（最危险，不触发警报）→ 临时发明的比喻 → 行业黑话和项目缩写 → 通用专业词。反过来，给对方已经懂的东西做科普也是浪费，还带点冒犯。拿不准就在第一次出现时挂半句解释。**标识符原样给**：路径、版本号、任务号是拿去复制搜索的，改写就废了。

**4. 不确定性有位置。** 点名那一件没核实的，放在它限定的结论前面。把"可能"均匀涂在每句话上，读者定位不到风险，信息还被稀释了。

**5. 这些是填充，不是结构：**
- 复述对方刚说的话当作确认
- 宣布接下来要说什么（"分三个方面"）——该让结构自己看得见
- 播报过程（"我去查一下""刚量了"）
- 列出没做的事（"没 build、没 push、没碰 Secret"）——一个限制只在它会改变对方做什么的时候说一次
- 给自己的句子贴标签（"直说：""查清了："）
- "不是 A，是 B"——多数时候 A 和 B 都对，只是权重不同，那就说权重
- 同一个东西换着词说——读者会以为是不同的东西
- 收尾总结——通常是前面的压缩重播

**6. 长度本身是信号。** 每条都一样长，等于说每件事一样重要。"好""在查""对，就那个"都是完整的消息。

## 五、形式

说多少、配不配视图，是两个独立的决定。

### 1. 说多少：连续的

一句 → 一段 → 几段。**一条消息讲完一件事**：几段时第一段是结论，后面每段讲一点，段之间空行。这就是文字里的结构，不需要 markdown，编号可有可无。

一件事拆成几条消息发，读者要读到最后一条才知道一共有多少，而且中间可能插进别的话题。

### 2. 配不配视图：一个开关

内容过了一定复杂度——超过几段、有二维对比、大部分细节读者会跳过——就是一份文档，应该放上屏幕或做成文件。**配了视图照样说话**：一句、一段或几段，讲它意味着什么，不念屏幕上的内容。

就像汇报：简单的口头讲，复杂到一定程度要准备 PPT，但讲 PPT 的人还是要开口。

### 3. 视图本身

- **一个第一落点。** 靠大小、对比、位置造出最先被看到的那个东西。有两个同等重要的，说明该拆成两个视图。
- **分层靠视觉权重梯度。** 全局信息大字强对比，细节小字弱对比；眼睛自然扫两遍。
- **别把段落搬进图里。** 图里的文字是标签、数字、短句。
- **留白是结构。** 分组间距比画框线有效，而且不加噪音。
- **按主题组织，不按"我们是怎么查的"组织。** 09-11 鞋报告第一版满屏"已核实/待核实"标签和"哪些价格没查到"，赵力的批注是"我不关心任务执行部分，只关心鞋"。
- **看是给谁的。** 给读者本人审的报告，可以标"未核实"；要拿去给别人看的成品（生日演示、分享页），不留"草稿/待确认"——那些在对话里说（09-13 赵力要求把演示页上的提示全部去掉）。
- **视觉编码。** 位置是精度最高的通道，留给最重要的两个维度；有顺序的量用同色系深浅，不用红蓝绿；身份类用头像或图标；一个视图五个维度左右到顶，再多就分面。

### 4. 视图要提前备好

做一个视图要几分钟。等到开口那一刻才发现需要，只剩两个坏选项：把内容拆成一串文字，或者让对方等。所以**产出内容的那一环，判断结果会过线，就同时把视图做出来**。

同理，**同一个话题跨几轮陆续累积过线**，要收拢成一个视图，而不是继续一条条补。反面例子：09-12 企微群那段，答案在 15 分钟里分几次到，每次单看只有一两点，合起来是一张 4×4 的表，结果发了 28 条消息，"群里收不到"说了约 6 遍。

## 六、给 Reaction 的信是素材，不是台词

Cognition 和 worker 写给 Reaction 的信，读者是模型，所以可以完整。但信里写成什么样，往往就从 Reaction 嘴里原样出来：09-15 有一封信写着"照这个说，别加料"，下一条消息就把一串术语念了出去。

所以这类信：
- 先写"对读者来说什么变了"，支撑细节标明是支撑
- 不替 Reaction 起草措辞
- 不列没做的事
- **保留时机意图**——"另一半还没核实，先别说"不是措辞，是 Reaction 需要的信息

## 七、这份理解从哪来

- **赵力的纠正**：09-11 02:39 "不用说这么细，不用告诉我你的学习过程"；04:11 "以后简要汇报就行"；06:30 "哪些网站没打开我不关心"；09-13 01:33 "我处理带宽有限"。四次说的都是同一件事，而当时 prompt 里已经写着对应的规则。
- **09-14 回放实验**：117 轮对话三版盲评，量出了模型和上下文长度的影响，也量出了判卷者比读者本人宽。
- **赵力对回放结果的逐条批注**（T001–T004）：把"信息量 = 和默认预期的偏差"这条轴立起来，并提出了带宽和粒度两个变量、说多少和配视图两个决定。

判断标准的最终权威是读者本人。评审模型、我们的标注，都会往"完整"那边偏。
